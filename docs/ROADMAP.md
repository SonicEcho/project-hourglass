# 本格開発のマイルストーン

> **2026-10-07 書き直し（開発者と確認して決定）**：M1 以降を、決まった物語（`docs/STORY.md` の 2-8〜2-12。8章＋終章、本編35〜45時間）に合わせて書き直した。M4 だった「後半〜終盤」を、M4（6〜7章）と M5（8章〜エピローグ）に分け、磨き込みと公開を M6 にした。

2026-10-06 時点のたたき台。試作（`docs/SPEC.md` の段階1〜9）の結果を受けて、製品版までの道のりを整理する。期限は決めず、作り込みを優先するので、日付は入れていない。

## 決まっていること（2026-10-06）

| 項目 | 決まったこと |
| --- | --- |
| 配布 | 最終的には**買い切りのアプリ**として配布する。開発は今の Web のまま進め、限界が来たらアプリに切り替える |
| 体制 | 開発は**1人**。期限は決めず、**とことん作り込む** |
| 絵と音 | **フリー素材と AI で作った素材**を使う |
| 用語と名前 | **M0 で先に決める**（候補の一覧は `docs/NAMING.md`） |
| 物語の長さ（2026-10-07） | **本編35〜45時間**。ペルソナや FF のように、物語がしっかりしていて、燃えて、泣けて、感情移入できるものにする。そのために物語を深掘りしてから章を組む（物語の背骨 → 章立て → 仲間の心の変化 → 伏線の表 → 日常の絆の出来事。`docs/STORY.md`） |

## 0. 出発点：試作でわかったこと

| 確かめたこと | 結果 |
| --- | --- |
| 戦闘（ラウンド制、共通の手札、コンボ、弱点・延長・バトン、連携技、部位破壊、大技の予告） | 段階6でCTBからラウンド制へ作り直した。ボスの手応えは「ちょうどいい」 |
| 育成1：星図（量の成長） | 確認済み。気になる点なし |
| 育成2：ムーブメント（詰めて組み合わせる成長） | 「いい感じのバランスで面白かった」 |
| 育成3：武器ビルドアップ（育てて分岐する成長）＋素材の断片化 | 実装済み。遊んだ感想はこれから |
| スマホ縦持ち・片手の操作 | 戦闘・3つの育成の画面とも、タップと長押しで組めた |
| 数値の決め方 | 自動対戦で勝率を測ってから決めるやり方が使えた |

**まだ確かめていないこと（本格開発で一番の不安）**

- 物語・探索・日常パートと組み合わせた時に、1回の遊び（数分〜30分）が気持ちよく区切れるか
- 時間を返すくり返し（探索 → コマを集める → 返す → 翌日に持ち主に会う）と、返すか残すかの選択が、遊びとして楽しく、物語として刺さるか
- 育成の仕組みが4つ重なった時に、初めての人が迷わないか（段階的な開放でさばけるか）
- 絵と音が入った時の見た目と手触り（いまは図形と文字だけ）

## 1. 進め方の方針

- **縦に切って作る**：仕組みを横に広げる前に、「1区画を製品の品質で」遊べる形（垂直スライス）を先に作り、外の人に遊んでもらう
- **章ごとに積む**：その後は、物語の章の順に作る。各章の終わりで、通しで遊べる状態にする
- **今の作り方を引き継ぐ**：`src/core` は Phaser に依存させない、数値は `src/data`、乱数はシード付き、テストが通らなければ公開しない、数値は自動対戦で測って決める
- **仕様書の分け方を変える**：`docs/SPEC.md` は試作の記録として残す。本格開発では、仕組みごとの設計書（戦闘・育成・探索・物語・時間を返す仕組みなど）と、マイルストーンごとの作業の一覧に分ける（段階14で実施：`docs/design/` と `docs/milestones/`）
- **1人で作り込むための工夫**
  - 各マイルストーンを、さらに今の「段階」の大きさ（1回の依頼でできて、スマホで確かめられる単位）に分けて進める。いつでも通しで遊べる状態を保つ
  - 期限がない分、範囲が広がり続けないように、マイルストーンごとに「ここまでできたら次へ」の基準を先に決める。作り込みは M6 だけでなく、各マイルストーンの終わりに「磨きの段階」を1つ入れる
  - 手で確かめる量を減らす：テスト、自動対戦の測定、画面のスクリーンショットの比較などを、できるだけ自動にする
- **アプリへの切り替えを見越した作り方**（Web のまま進めても、後でアプリに包めるように）
  - アプリに包む方法は、今のコードをそのまま使える Capacitor などを第一候補にする（作り直しにならない）
  - セーブは「保存する場所」を1か所にまとめて、Web の保存先とアプリの保存先を差し替えられる形にする
  - サーバーを使わない（買い切りでオフラインでも遊べるように）。インターネットが要るのは素材の読み込みだけにして、それもアプリでは中に同梱する
  - 切り替えを考える目安：画面の重さ（古いスマホで動きがかくつく）、ブラウザの保存の制限（容量、消える心配）、音の再生の制限、ストアで売る準備を始める時（遅くとも M6 の前）

## 2. マイルストーン

### M0：本格開発の土台（2026-10-08 完了）

試作のコードを、長く育てられる形に整える。遊びの中身はほぼ増やさない。

- **決めること**
  - 用語と名前（最初に決める）：`docs/NAMING.md` の一覧から選ぶ。ゲームのタイトル、仕組みの名前、キャラ名。決めたら、コード・画面・文書をまとめて書き換える
  - エンジン：Phaser 3 を続けるか（探索や会話の画面まで作れるか、を小さく試してから決める）
  - 絵と音の方向性：フリー素材と AI で作る素材の見た目をそろえるため、画面の解像度、絵柄（ドット絵か、イラスト調か）、色の決まりを先に決める
- **作るもの**
  - セーブ・ロード（版の番号付き。データの形が変わっても古いセーブを読めるように）。中断・再開（まずは戦闘の外だけ）
  - データの定義をまとめ直す（キャラ・敵・スナップ・ギア・武器・素材を、表で書いて読み込む形に。数が増えても管理できるように）
  - 画面の移り変わりと状態の持ち方を整理（今の `run.ts` を、章・日・区画を持てる形に）
  - 自動対戦の勝率測定をスクリプトにして、いつでも回せるようにする
  - 設計書の分割（上の「仕様書の分け方」）
  - 素材台帳の仕組み（下の「絵と音の素材の管理」）。素材を読み込む部品を1か所にまとめ、仮の素材と本番の素材を差し替えやすくする
- **完成の基準**：今の試作と同じ遊びが、新しい土台の上で動く。途中で閉じても続きから遊べる

### M1：垂直スライス（プロローグと1章の最初）

「このゲームはこういう遊び」が1回で伝わる、30〜45分の体験を製品の品質で作る。物語は `docs/STORY.md` の 2-8〜2-12。

- **作るもの**
  - プロローグ：7歳の3人の夏祭り（名前の札のない語りの文と、砂の演出。6章のどんでん返しの仕込みも、ここから入れる）
  - 1章の日常1日：昼の街（学校・商店街・時計屋）、絆の出来事1つ、小話1つ
  - りくが消える → 時計屋の奥の入口 → レストピアの蔵書の棚
  - 1-1「金魚の名前」の1区画：探索（移動、砂嵐との遭遇、宝箱・素材、チェックポイント）、コマ集め（「あとコマが3つで返せる」）、区画の奥のボス
  - 時間を返す場面と、翌日の昼に持ち主（大学生）が妹に電話をかける場面
  - 最後に、ノアとのすれ違い（「……どうして、あなたがここに」）で次へ引く
  - 仕組み：会話の画面（段階16の試作を製品にする）、探索（`src/core/grid.ts` を使う）、昼の日常の枠、コマ集めと返す仕組み
  - 戦闘：今のものに加えて、雑魚戦のオート（作戦指定）と早送り。敵は平成の砂嵐
  - 育成：星図と武器だけを開放
  - 初めての人向けの説明（戦闘・育成を、遊びながら少しずつ覚える）
  - 絵と音：このスライスの範囲だけ、製品に近い品質で入れる
- **完成の基準**：開発に関わっていない人5〜10人に遊んでもらい、「続きを遊びたいか」を聞く。どこで迷ったか・やめたかを記録する
- **ここでの判断**：結果しだいで、探索・日常・戦闘の比重や、育成を開放する順番を見直す

### M2：1〜2章（前半の土台：取り戻して返すくり返し）

  - 絆の出来事と小話の仕組み（あかり・みお。1〜5章は、りくの調査ノートの回想の小話も）

## 3. マイルストーンをまたいで進めること

| 流れ | 内容 | 始める時期 |
| --- | --- | --- |
| 物語・脚本 | 章ごとの筋、会話、伏線と回収の表（`docs/STORY.md` の 2-11）、絆の出来事と小話の台本 | M0 から。各マイルストーンの前に、その範囲の脚本を固める |
| 絵・音 | 方向性 → スライスの範囲 → 章ごとに量産。フリー素材と AI で作る素材を、台帳で管理する | M0 で方向性と台帳、M1 で最初の製品品質 |
| 数値の調整 | 自動対戦の測定を各マイルストーンの終わりに回す。成長の量（育成4つ分）の上限を決めておく | ずっと |
| 試遊 | 開発に関わっていない人に遊んでもらう | M1 から、各マイルストーンの終わりに |
| 技術 | セーブの版の管理、性能、端末対応 | M0 から |

## 4. 絵と音の素材の管理（フリー素材・AI で作る素材）

買い切りで売るので、使う素材はすべて「売り物に使ってよいか」を確かめられる状態にしておく。

- **素材台帳**（`docs/ASSETS.md` などの表）に、素材ごとに次を書く：ファイル名、どこで手に入れたか（サイトの名前と URL、または使った AI のサービス名）、ライセンスの名前、売り物に使えるか、作者の名前の表示（クレジット）が要るか、改変してよいか、手に入れた日
- **フリー素材**：「フリー」でも、売り物での利用、改変、クレジットの表示に条件があることが多い。素材ごとに利用規約を読み、台帳に書く。規約は変わることがあるので、手に入れた時の規約を保存しておく
- **AI で作る素材**
  - 使うサービスの利用規約で、作ったものを売り物に使えるかを確かめる（無料の版と有料の版で違うことがある）
  - 特定の作家や作品の名前を指示に入れて、似せた絵を作らない
  - 見た目をそろえるため、使った指示（プロンプト）と設定を台帳に残す
  - ストアによっては、AI で作った素材を使っていることの申告を求められる（たとえば Steam）。アプリのストアの最新の決まりを、公開の前に確かめる
- **クレジット表示**：台帳から、タイトル画面や「クレジット」の画面に出す一覧を作れるようにする
- 素材の権利が心配なものは、公開前に差し替えられるよう、素材を読み込む部品を1か所にまとめておく（M0）
