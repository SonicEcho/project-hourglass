# 設計書：技術・テスト・デバッグ

## 1. 技術の構成

| 項目 | 使うもの | 用途 |
| --- | --- | --- |
| 言語 | TypeScript | 型で壊れにくくする |
| ビルド | Vite（`base` は `/project-hourglass/`） | 開発と本番ビルド |
| 描画 | Phaser 3 | 2Dの画面、タップ操作、アニメーション |
| テスト | Vitest | ロジックの自動テスト |
| CI・公開 | GitHub Actions → GitHub Pages | push でテストし、通れば `main` だけ公開 |
| スマホ用ログ | eruda（`?debug=1` の時だけ読み込む） | スマホのブラウザでエラーやログを見る |

- Node.js は 22
- 画面は縦持ち 390×844 を基準に、Phaser の Scale FIT で合わせる。高解像度のスマホでにじまないよう、内部は端末の画素密度（最大3倍）で描き、座標は 390×844 のまま
- サーバーは使わない（買い切りでオフラインでも遊べるように。`docs/ROADMAP.md`）
- エンジンは Phaser 3 を続ける（段階16の試作で決めた。下の「決定の記録」）

## 2. フォルダ

| 場所 | 中身 |
| --- | --- |
| `src/core/` | ゲームのロジック（戦闘、星図、ムーブメント、武器、進み具合、セーブ、マス目の地図と道探し）。Phaser もブラウザの機能も読み込まない。状態を受け取り、新しい状態を返す |
| `src/data/` | 数値とデータ（キャラ、魔法・スキル、スナップ、コンボ、連携技、敵、星図、ギア、武器、周回、物語の章・区画）。ロジックに数値を直書きしない |
| `src/scenes/` | Phaser の画面と、周回の状態（`run.ts`） |
| `src/ui/` | 画面の部品、文字、配置、色 |
| `src/save/` | 保存の窓口（今は localStorage） |
| `src/assets/` | 素材を読み込む部品（`loader.ts`）と、クレジットの一覧を作る処理（`credits.ts`） |
| `public/assets/` | 絵・音などの素材のファイル（台帳は `src/data/assets.ts`、決まりは `docs/ASSETS.md`、絵の方向性は `docs/ART.md`）。立ち絵は `portraits/` に WebP で置く |
| `src/sim/` | 自動対戦（決まった方針で自動で遊ぶ）と測定の集計 |
| `src/tools/` | 開発用の道具の処理（データの一覧表を作る `dataTables.ts`） |
| `src/debug/` | デバッグメニュー、戦闘ログ、チート、eruda、ビルド情報 |
| `tests/` | Vitest のテスト（`tests/core/` がロジック） |
| `scripts/` | 開発用の命令（`measure.mjs`、`data-tables.mjs`）と、立ち絵の背景を抜く `cutout.py`（Python。`pip install "rembg[cpu]"` が要る。アニメ向けの背景を抜く AI を使う） |
| `docs/` | 文書（`docs/design/README.md` の一覧）。`docs/licenses/` は利用規約・ライセンス文の控え。`docs/data/` はデータの一覧表（自動で作る） |

## 3. 設計の原則

- **ロジックと画面を分ける**：`src/core` は Phaser を一切読み込まない。自動テストで確かめられる形にする
- **データはコードから分ける**：数値は `src/data` に TypeScript で書く（型とテストで書き間違いを見つける）。表で見たい時は `docs/data/` の一覧表を見る（`npm run data:tables` で自動で作る）
- **乱数はシードで再現できる**：乱数は mulberry32。戦闘の状態に乱数の内部状態も持つ。URL の `?seed=数字` で固定できる
- **戦闘の出来事は記録に残す**：すべて `state.log` に構造化して残し、演出・戦闘ログ・行動の回数に使う
- **保存の場所・素材の読み込みは1か所にまとめる**：Web とアプリで差し替えられるように
- **素材がなくても止まらない**：ゲームの始めの「起動」の画面（`BootScene`）で台帳の素材を読み込む。画面は台帳の id で素材を使い（`addImageOr`）、読み込めない時は図形で代わりに描く。読めなかった素材はコンソールに `[assets]` 付きで出す

## 4. テスト

- `npm test` で全部。`src/core` を変えたら、必ず `tests/` のテストを足す・直す
- データのつながり（`tests/dataRefs.test.ts`。敵が落とす素材、戦闘の報酬、コンボの材料、星図のマスなどが、本当にある名前を指しているか）と、一覧表が今のデータと同じか（`tests/dataTables.test.ts`。データを変えて `npm run data:tables` を忘れると失敗する）
- 素材台帳の書き漏れ（`tests/assets.test.ts`。ファイルがない、クレジットの文がない、規約の控えがない、本番なのに売り物に使えない、ライブラリが `package.json` と合わない）
- ロジック（戦闘・星図・ムーブメント・武器・進み具合・セーブ）、データの整合（`tests/data.test.ts` など）、Phaser に依存しない補助関数（デバッグ判定、ビルド情報、スキルの並べ方）、自動対戦（`tests/sim.test.ts`）
- コミットの前に `npm test`、`npx tsc --noEmit`、`npm run build` がすべて通ること

## 5. 自動対戦の測定

- `npm run measure`（`-- --runs 200 --seed 1` で回数とシード）。結果は戦闘ごとの「1回目で勝てた割合」「平均ラウンド」「平均やり直し」の表。同じ回数・シードなら同じ結果。200周で約20秒
- GitHub Actions の「Measure」（`.github/workflows/measure.yml`）：`main` への push と手での実行で回り、結果は Summary に出る。公開とは別
- 自動の方針（`src/sim/`）

| 場面 | 方針 |
| --- | --- |
| 戦闘 | 候補の先頭5つからでたらめに選ぶ。サポートは半分の確率で使う。追加行動は3回に1回バトンタッチ |
| 星図 | でたらめなキャラの、開けられるでたらめなマスに、払えなくなるまで使う |
| ギアの報酬 | 候補の先頭から選ぶ |
| ムーブメント | 戦闘の前に全部外し、大きいギアから順に、効果ギアはブリッジ優先、狂いを作らない場所へ。キャラは順番に回す |
| 武器 | 素材・アイテムはすべて時分解し、欠片をでたらめな武器へ。進化できれば最初の進化先 |
| 負けた時 | 育成はそのまま、同じ戦闘を別のシードでやり直す（最大20回） |

- 数値を変える時は、測ってから決める。測った結果は、変えた設計書の「決定の記録」に残す

## 6. デバッグ（スマホで確かめるため）

- 開発者はスマホのブラウザで公開URLを開いて確かめる。PCの開発者ツールは使えない前提
- 画面右下に、ビルドした日時（日本時間）とコミットの短いIDを出す（`YYYY-MM-DD HH:mm JST (abc1234)`。`?debug=1` の時は先頭に `[debug]`）
- `?debug=1` の時だけ、eruda と、左下の「DBG」から開くデバッグメニュー（Phaser の外の HTML）を有効にする
  - 味方を全回復／敵のHPを1にする（演出中は使えない）
  - 星の砂 +10／ギアを全種類もらう／素材とアイテムを全種類もらう／3人の武器を Lv3 にする
  - ボス戦（最後の戦闘）から始める
  - セーブの中身を見る／セーブを消す
  - 試作：探索の画面・会話の画面を開く（段階16。エンジンを決めるため。本編では使わない）
  - シードの表示・固定・指定して最初から
  - 戦闘ログ（ラウンドの区切り、追加行動）
- コンソールには `[battle]` `[save]` などの印を付けて出す

## 7. 公開

- `.github/workflows/deploy.yml`：すべてのブランチへの push と PR でテストとビルド。GitHub Pages への公開は `main` への push の時だけ。テストかビルドが1つでも失敗したら公開しない
- リポジトリの Settings → Pages の Source は「GitHub Actions」
- 公開URL：https://sonicecho.github.io/project-hourglass/

## 決定の記録

試作の経緯は `docs/SPEC.md` の「実装時の決定事項」。段階14以降で技術の決まりを変えたら、ここに日付・段階・理由を1〜2行で足す。

- 2026-10-08 段階18a：AI で作った立ち絵は、背景を `scripts/cutout.py`（背景を抜く AI、rembg の isnet-anime。色の近さで抜く自前の処理は髪のまわりに白いふちが残ったのでやめた）で透明に抜き、WebP（透明あり、1枚約120KB）で置く。PNG より軽く、スマホのブラウザで読める。話していない人の立ち絵は、重なっても透けないよう、薄くするのではなく暗くする
- 段階17：データは TypeScript のまま書き、表は自動で作ると決めた（開発者と相談。数値は Claude に頼んで変える形なので、型とテストで守れる方を取った）。表は画面と同じ説明の処理で作り、表が古いとテストが失敗する
- 段階16：エンジンを決めるために、探索（タップで歩く、カメラが追う、敵の印が行き来する）と会話（文字送り、選択肢、ログ、早送り）の試作を Phaser 3 で作った。Phaser の機能（カメラの追従と範囲、2つ目のカメラで画面の文字を固定、tween、タイマー、文字の折り返し）で足りた。手間がかかったのは、拡大した画面で文字とボタンを固定するために、地図用と文字用のカメラを分けた所だけ。GPU のない環境で測ったコマ数は、探索 13〜14・会話 13・戦闘 10（どれも同じくらい遅い環境なので比べるだけ）で、探索・会話は今の戦闘より軽い。続けるかは開発者のスマホでの感想を聞いて決める
- 2026-10-07 段階16：**エンジンは Phaser 3 を続ける**と決めた。開発者のスマホ（Pixel 5a）で、探索の試作が59fps以上を保ち、滑らかさ・会話の文字・操作の手触りとも「とても良かった」
- 段階15：素材台帳の正は `src/data/assets.ts`（クレジットの画面とテストが同じものを読む）。配布物に入るライブラリ（Phaser、eruda）も台帳に載せる（MIT は売り物でも使えるが、著作権表示が要る）
- 段階12：`npm run measure` は、TypeScript のまま読み込むため Vite の `runnerImport` を使う（道具を増やさない）
