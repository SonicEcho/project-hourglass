# 設計書：技術・テスト・デバッグ

## 1. 技術の構成

| 項目 | 使うもの | 用途 |
| --- | --- | --- |
| 言語 | TypeScript | 型で壊れにくくする |
| ビルド | Vite（`base` は `/project-hourglass/`） | 開発と本番ビルド |
| 描画 | Phaser 3 | 2Dの画面、タップ操作、アニメーション |
| テスト | Vitest | ロジックの自動テスト |
| CI・公開 | GitHub Actions → GitHub Pages | push でテストし、通れば `main` だけ公開 |
| スマホ用ログ | eruda（`?debug=1` の時だけ読み込む） | スマホのブラウザでエラーやログを見る |

- Node.js は 22
- 画面は縦持ち 390×844 を基準に、Phaser の Scale FIT で合わせる。高解像度のスマホでにじまないよう、内部は端末の画素密度（最大3倍）で描き、座標は 390×844 のまま
- サーバーは使わない（買い切りでオフラインでも遊べるように。`docs/ROADMAP.md`）
- エンジンは Phaser 3 を続ける（段階16の試作で決めた。下の「決定の記録」）

## 3. 設計の原則

- **ロジックと画面を分ける**：`src/core` は Phaser を一切読み込まない。自動テストで確かめられる形にする
- **データはコードから分ける**：数値は `src/data` に TypeScript で書く（型とテストで書き間違いを見つける）。表で見たい時は `docs/data/` の一覧表を見る（`npm run data:tables` で自動で作る）
- **乱数はシードで再現できる**：乱数は mulberry32。戦闘の状態に乱数の内部状態も持つ。URL の `?seed=数字` で固定できる
- **戦闘の出来事は記録に残す**：すべて `state.log` に構造化して残し、演出・戦闘ログ・行動の回数に使う
- **保存の場所・素材の読み込みは1か所にまとめる**：Web とアプリで差し替えられるように
- **素材がなくても止まらない**：ゲームの始めの「起動」の画面（`BootScene`）で台帳の素材を読み込む。画面は台帳の id で素材を使い（`addImageOr`）、読み込めない時は図形で代わりに描く。読めなかった素材はコンソールに `[assets]` 付きで出す

## 4. テスト

- `npm test` で全部。`src/core` を変えたら、必ず `tests/` のテストを足す・直す
- データのつながり（`tests/dataRefs.test.ts`。敵が落とす素材、戦闘の報酬、コンボの材料、星図のマスなどが、本当にある名前を指しているか）と、一覧表が今のデータと同じか（`tests/dataTables.test.ts`。データを変えて `npm run data:tables` を忘れると失敗する）
- 素材台帳の書き漏れ（`tests/assets.test.ts`。ファイルがない、クレジットの文がない、規約の控えがない、本番なのに売り物に使えない、ライブラリが `package.json` と合わない）
- ロジック（戦闘・星図・ムーブメント・武器・進み具合・セーブ）、データの整合（`tests/data.test.ts` など）、Phaser に依存しない補助関数（デバッグ判定、ビルド情報、スキルの並べ方）、自動対戦（`tests/sim.test.ts`）
- **通しの自動確認**（`npm run e2e`、`scripts/e2e.mjs`。段階20）：`npm run build` した公開物を手元のサーバーで開き、Playwright の Chromium で自動で遊ぶ。タイトル →「はじめる」→ 戦闘1〜5（デバッグの「敵のHPを1にする」と「自動で1ラウンド戦う」で進める）→ 結果。戦闘2の後にページを開き直して「つづきから」で続くか、BGM が流れて縁日の試作で切り替わるかも見る。エラーが出たり止まったりしたら失敗し、その時の画面を `e2e-failure.png` に残す。1回およそ1分
  - 画面は canvas なので、ボタンは文字の位置を `window.__restopia.findText()` で調べてタップする。画面の文字を変えたら、`scripts/e2e.mjs` の探す文字も合わせる
- コミットの前に `npm test`、`npx tsc --noEmit`、`npm run build`、`npm run e2e` がすべて通ること

## 5. 自動対戦の測定

- `npm run measure`（`-- --runs 200 --seed 1` で回数とシード）。結果は戦闘ごとの「1回目で勝てた割合」「平均ラウンド」「平均やり直し」の表。同じ回数・シードなら同じ結果。200周で約20秒（1-1 の表を含めて約30秒）
- GitHub Actions の「Measure」（`.github/workflows/measure.yml`）：`main` への push と手での実行で回り、結果は Summary に出る。公開とは別
- 自動の方針（`src/sim/`）

| 場面 | 方針 |
| --- | --- |
| 戦闘 | 候補の先頭5つからでたらめに選ぶ。サポートは半分の確率で使う。追加行動は3回に1回バトンタッチ |
| 星図 | でたらめなキャラの、開けられるでたらめなマスに、払えなくなるまで使う |
| ギアの報酬 | 候補の先頭から選ぶ |
| ムーブメント | 戦闘の前に全部外し、大きいギアから順に、効果ギアはブリッジ優先、狂いを作らない場所へ。キャラは順番に回す |
| 武器 | 仲間を順番に回し、一番近い進化先に近づく素材から吸わせる（枠がいっぱいになるまで。鍵の素材は残す）。残りは時分解し、欠片をでたらめな仲間へ。進化できれば最初の進化先（`src/sim/autoArmory.ts`。段階27b） |
| 負けた時 | 育成はそのまま、同じ戦闘を別のシードでやり直す（最大20回） |

- **1-1 の縁日の表**（段階27。`src/sim/autoArea.ts`）：章のパーティ（ハルトとあかり）で、区画の戦闘を出会う順（敵の印の並び → ボス）に戦う。最初の戦闘の後に宝箱を2つとも開ける。星図はパーティの中ででたらめ、武器は上の表と同じ、ムーブメントはなし。つながりゲージは戦闘をまたいで引き継ぐ。戦闘の方針を2つ出す
  - ほぼでたらめ：上の表と同じ
  - 弱点をねらう（`src/sim/autoBattle.ts` の `smartPlay`）：敵の本当の弱点を突く行動を最優先。なければ、力をためている敵がいる時は防御、弱点が隠れた部位を狙う、の順。連携技は体勢が崩れた敵がいる時だけ。追加行動は弱点を突ければ突き、なければ半分の確率でバトンタッチ
- 数値を変える時は、測ってから決める。測った結果は、変えた設計書の「決定の記録」に残す

## 6. デバッグ（スマホで確かめるため）

- 開発者はスマホのブラウザで公開URLを開いて確かめる。PCの開発者ツールは使えない前提
- 画面右下に、ビルドした日時（日本時間）とコミットの短いIDを出す（`YYYY-MM-DD HH:mm JST (abc1234)`。`?debug=1` の時は先頭に `[debug]`）
- `?debug=1` の時だけ、eruda と、左下の「DBG」から開くデバッグメニュー（Phaser の外の HTML）を有効にする
  - 味方を全回復／敵のHPを1にする（演出中は使えない）
  - 星の砂 +10／ギアを全種類もらう／素材とアイテムを全種類もらう／3人の武器を Lv3 にする
  - ボス戦（最後の戦闘）から始める
  - セーブの中身を見る／セーブを消す
  - 試作：探索の画面を開く（段階16。エンジンを決めるため。本編では使わない）
  - 会話：M1 を通しで読む、場面を選んで開く、読んだ印を消す（段階22）
  - シードの表示・固定・指定して最初から
  - 戦闘ログ（ラウンドの区切り、追加行動）
- コンソールには `[battle]` `[save]` などの印を付けて出す

## 7. 公開

- `.github/workflows/deploy.yml`：すべてのブランチへの push でテストとビルド（PR の時は走らせない。push の結果が PR にも出るため）。Playwright のブラウザは版ごとに覚えておき（actions/cache）、毎回は入れ直さない。GitHub Pages への公開は `main` への push の時だけ。テスト・ビルド・通しの自動確認のどれか1つでも失敗したら公開しない（通しの自動確認が失敗した時の画面は、その実行の Artifacts の `e2e-failure` に残る）
- リポジトリの Settings → Pages の Source は「GitHub Actions」
- 公開URL：https://sonicecho.github.io/project-hourglass/

## 決定の記録

試作の経緯は `docs/SPEC.md` の「実装時の決定事項」。段階14以降で技術の決まりを変えたら、ここに日付・段階・理由を1〜2行で足す。

- 2026-10-09 段階32a 調整2：小さなアイコンは絵の素材を使わず、図形で描く（`src/ui/icons.ts`）。図形の丸や星（`add.circle`・`add.star`）を tween で拡大・移動させると、画面に描かれないことがあった（物はあり、表示の設定も正しいのに写らない。原因は突き止めていない）。動く光の粒は粒子（`add.particles`）で、広がる輪やきらめきは Graphics を毎回描き直す形で作る
- 2026-10-09 段階32a 調整1：画面の動き（画面に入る演出、ボタンの光と砂、窓の出し入れ、数を数える・ゲージが滑らかに動く）と、戦闘画面の見た目（地面・影・光、はねるダメージの数字、行動順の顔、浮き上がるカード）を足した。動きの長さは `MOTION`、戦闘の地面の色は `STAGE`（`src/ui/theme.ts`）。HP の数え始めは前に出した値を覚えておく（`battleViews.ts` の `previousValue`。戦闘の始めに空にする）。行動順の顔は立ち絵から丸く切り出す（切り出す範囲 `FACE_CROP` は全員同じ構図なので共通）。ゲームの画面は iPhone の安全な領域の中に置く（`index.html`）
- 2026-10-09 段階32a：開発者の「UI がシンプル過ぎる」から、画面の部品の見た目を作り直した（絵の素材は使わず図形で描く）。背景は藍から紺へ移る色と舞う砂（`screenBg`。描き直しのたびに作り直さないよう、画面ごとに1回だけ作る）、ボタンは角丸・影・光・押すと沈む、説明や詳しい情報の窓は四隅に飾り（`addWindow`）、ゲージは角丸に光の筋。Phaser 3.90 の角丸は角を「半径÷5」個の辺で描き、面取りに見えたので、`skin.ts` で角を8辺以上で描くよう置き換えた。見出しとボタンの文字（太字の文字）は Zen Maru Gothic の太字（SIL OFL）にした。日本語の書体は 3.7MB あるので、`src/` に書かれている字＋かな・英数字だけに絞って 192KB にした（新しい字が増えたらテストが知らせる。作り直すのは `python3 scripts/font-subset.py`）。書体は起動の画面で読み込み、3秒たっても読み込めなければ端末の文字で進む
- 2026-10-08：Actions の待ち時間を縮めた。PR の時の確認をやめて push の時の1回だけにし（同じ確認が2回走っていた）、Playwright のブラウザを版ごとに覚えておく形にした（開発者と相談）
- 2026-10-08 段階20：通しの自動確認を Actions に入れ、M0 の完成の基準（同じ遊びが動く、途中で閉じても続きから遊べる）を公開のたびに確かめる。戦闘は自動対戦の方針（`src/sim/autoBattle.ts` の `autoPlan`・`autoExtra`）を戦闘画面から呼んで進める（測定の結果は切り出す前と同じ）。BGM は mp3 にし（約0.9MB → 約0.2MB）、くり返しは Phaser の音を使わず Web Audio の区間ループ（`loopStart`・`loopEnd`）に直接任せる（Phaser の区間（マーカー）は、区間の前から区間へ移る時に切れ目ができるため。曲の切り替えのフェードも画面に依存しなくなった）。mp3 は頭と終わりに無音が入るので、仮の BGM は1周の前後に0.5秒ずつ足して書き出し、区間だけをくり返す
- 2026-10-08 段階19：音は `src/audio/sound.ts` だけで鳴らす。BGM はゲーム全体で1曲で、画面が替わっても止めず、別の曲を頼まれた時だけ前の曲を0.6秒で小さくして切り替える（戦闘や星図に入ってもタイトルの曲が続く）。くり返す区間は `src/data/sounds.ts` の `BGM_LOOPS` に曲ごとに書く（Suno の曲のつなぎ目用。書かなければ曲の全体をくり返す）。音量の設定はセーブとは別に保存する（`restopia.settings`。セーブを消しても音量は残る）。スマホのブラウザは最初に触れるまで音を出せないので、その前に頼まれた BGM は触れた後に始め、効果音は鳴らさない。戦闘を早送りしている間は効果音を鳴らさない
- 2026-10-08 段階18a：AI で作った立ち絵は、背景を `scripts/cutout.py`（背景を抜く AI、rembg の isnet-anime。色の近さで抜く自前の処理は髪のまわりに白いふちが残ったのでやめた）で透明に抜き、WebP（透明あり、1枚約120KB）で置く。PNG より軽く、スマホのブラウザで読める。話していない人の立ち絵は、重なっても透けないよう、薄くするのではなく暗くする
- 段階17：データは TypeScript のまま書き、表は自動で作ると決めた（開発者と相談。数値は Claude に頼んで変える形なので、型とテストで守れる方を取った）。表は画面と同じ説明の処理で作り、表が古いとテストが失敗する
- 段階16：エンジンを決めるために、探索（タップで歩く、カメラが追う、敵の印が行き来する）と会話（文字送り、選択肢、ログ、早送り）の試作を Phaser 3 で作った。Phaser の機能（カメラの追従と範囲、2つ目のカメラで画面の文字を固定、tween、タイマー、文字の折り返し）で足りた。手間がかかったのは、拡大した画面で文字とボタンを固定するために、地図用と文字用のカメラを分けた所だけ。GPU のない環境で測ったコマ数は、探索 13〜14・会話 13・戦闘 10（どれも同じくらい遅い環境なので比べるだけ）で、探索・会話は今の戦闘より軽い。続けるかは開発者のスマホでの感想を聞いて決める
- 2026-10-07 段階16：**エンジンは Phaser 3 を続ける**と決めた。開発者のスマホ（Pixel 5a）で、探索の試作が59fps以上を保ち、滑らかさ・会話の文字・操作の手触りとも「とても良かった」
- 段階15：素材台帳の正は `src/data/assets.ts`（クレジットの画面とテストが同じものを読む）。配布物に入るライブラリ（Phaser、eruda）も台帳に載せる（MIT は売り物でも使えるが、著作権表示が要る）
- 段階12：`npm run measure` は、TypeScript のまま読み込むため Vite の `runnerImport` を使う（道具を増やさない）
- 2026-10-10 段階32b 調整3：屋台めぐりの「けいかくひょう」に、子どもの手書き風の書体 Hachi Maru Pop（SIL OFL）を足した（はちまるポップ・よもぎ・Zen Kurenaido を見比べ、一番子どもの字らしいものにした）。かな・英数字と `src/data/daily.ts` の字だけに絞って 56KB（`hand.woff2`。`addText` の `hand`）。見出しの書体と一緒に起動の画面で読み込む
